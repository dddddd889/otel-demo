五个词各自在哪一层

名称含义项目中的例子最终查看
Resource描述“谁产生的数据”，会附加到三种信号上service.name、service.versionJaeger、Prometheus、Loki 都能用到
Trace一次请求的调用路径，由多个 Span 构成checkout → inventory → paymentJaeger
Metric在时间维度上聚合的数值checkout.requests、请求耗时直方图Prometheus / Grafana
LogRecord一条独立结构化日志严重级别、body、attributes、Trace IDLoki / Grafana Explore
instrumentations对 Express、HTTP、MySQL 等库进行 patch，自动创建遥测数据getNodeAutoInstrumentations()它自身不是可查询的信号

映射到 NodeSDK

new NodeSDK({
  resource,             // 三种信号共用的来源身份
  traceExporter,        // Span → OTLP Traces
  metricReaders,        // Metric 聚合后 → OTLP Metrics
  logRecordProcessors, // LogRecord 处理后 → OTLP Logs
  instrumentations,     // 自动 patch 库并创建遥测数据
});

Resource 不是每条业务请求的参数，而是进程、服务、容器或主机级别的身份。订单 ID 这类每次请求不同的数据，应该放在 Span Attribute 或 LogRecord Attribute，不应该放在 Resource。

数据流

业务请求
  → Instrumentation 或手动 API
  → Span / Metric / LogRecord
  → 附加 Resource: service.name=checkout-service
  → Processor / Reader
  → OTLP Exporter
  → Collector
  → Jaeger / Prometheus / Loki

即时自测

service.name 应放在 Metric Attribute 吗？

通常由 Resource 统一提供，无需在每次 Metric 记录时重复添加。

getNodeAutoInstrumentations() 是后端吗？

不是。它在应用进程内 patch 依赖库，自动生成 Span 等数据。

Trace 和 Span 是同一个层级吗？

不是。Trace 是整条调用链，Span 是其中的一段操作。
