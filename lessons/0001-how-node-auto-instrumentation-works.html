OpenTelemetry 原理课 · 01

自动插桩不是监听网络，它是在模块被使用前改写函数。

用三个完全隔离的进程对比同一次 HTTP 请求：没有插桩、自己 patch、官方 instrumentation。完成时间约 10 分钟，不需要 Docker，也不会启动现有业务服务。

你将亲手证明

Baseline
没有 Span，也没有 traceparent
Manual patch
改写 http.get，产生 CLIENT Span
Official
自动产生 CLIENT + SERVER Span

1. 先看没有插桩

npm run lab:auto:baseline

预期只出现：

[RESULT] mode=baseline downstream_traceparent=无

检查点：没有任何 [SPAN] 行。

2. 再启用手写 patch

npm run lab:auto:manual

预期出现一个 CLIENT Span，下游收到同一 Span 注入的 W3C Header：

[SPAN] name=manual-http-get kind=CLIENT trace_id=... span_id=...
[RESULT] mode=manual downstream_traceparent=00-TRACE_ID-SPAN_ID-01

打开 labs/auto-instrumentation/manual-http-patch.js，按这个顺序读：

  1. 保存原始 http.get。
  2. 把 http.get 替换为 patchedGet。
  3. 调用 startActiveSpan，使新 Span 成为当前 Context。
  4. 把当前 Context 注入请求 Headers。
  5. 调用原始函数，并在响应结束或错误时结束 Span。
  6. disable() 恢复原始函数。

3. 最后运行官方 HTTP instrumentation

npm run lab:auto:official

预期产生两个 Span：

[SPAN] name=GET kind=SERVER trace_id=同一个 parent_span_id=客户端SpanID
[SPAN] name=GET kind=CLIENT trace_id=同一个 parent_span_id=无

官方版本不仅包装客户端调用，还包装下游的 http.createServer 请求处理，并自动提取 traceparent，所以 SERVER Span 成为 CLIENT Span 的子级。

为什么必须先加载 instrumentation

node --require instrumentation.js app.js 的意义不是“后台监听”，而是让 patch 在业务代码首次加载 http、Express 等模块之前注册。模块已经加载并缓存后才启动 instrumentation，patch 可能来不及应用。

本实验特意把官方初始化文件放进 --require：

node --require ./labs/auto-instrumentation/official-instrumentation.js \
  labs/auto-instrumentation/run-lab.js official

即时自测

为什么这不叫“直接监听底层网络”？

因为核心动作是替换模块导出的函数或利用模块加载 Hook；网络调用仍由原始 http.get 完成，插桩只是在调用前后创建遥测并传播 Context。

为什么手写版本只有 CLIENT，没有 SERVER？

这个教学 patch 只替换了 http.get。官方 HTTP instrumentation 还覆盖服务端请求入口，并从 Header 提取父 Context。

Trace ID 和 Span ID 在 Header 中如何对应？

traceparent=00-TRACE_ID-SPAN_ID-01。下游保留 Trace ID，以 Header 中的 Span ID 作为 SERVER Span 的父级。
