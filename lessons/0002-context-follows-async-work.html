OpenTelemetry 原理课 · 02

Trace 不串线，靠的不是全局变量，而是异步上下文。

用两个并发任务依次验证全局变量、Node.js AsyncLocalStorage 和 OTel Context。约 10 分钟，不需要 Docker，也不占用业务端口。

先建立正确心智模型

普通变量
整个进程共享最后一次写入
AsyncLocalStorage
每条异步调用链拥有独立 Store
OTel Context
在 Store 中携带 Active Span 等值

Context 不是跨进程 Header。Context 解决当前进程、当前异步调用链里的状态传递；Propagation 才负责把 Context 注入 HTTP 或 MQ Header，交给另一个进程。

1. 亲手复现串线

npm run lab:context:global
[TASK] mode=global expected=A actual=B isolated=false
[TASK] mode=global expected=B actual=B isolated=true

A 先写入全局变量，等待期间 B 覆盖它，所以 A 恢复执行时读到了 B。这正是并发请求不能把 Trace ID 放普通全局变量的原因。

2. 用 AsyncLocalStorage 隔离

npm run lab:context:als
[TASK] mode=als expected=A actual=A isolated=true
[TASK] mode=als expected=B actual=B isolated=true

storage.run(store, callback) 激活 Store；在 callback 内创建的 Promise、Timer 等异步资源恢复执行时，getStore() 仍返回所属调用链的 Store。

3. 换成 OTel Context 与 Active Span

npm run lab:context:otel
[TASK] mode=otel expected=A actual=A isolated=true
[RELATION] task=A active_matches=true same_trace=true parent_matches=true

startActiveSpan 不只创建 Span，还在 callback 执行期间把它写入当前 Context。因此异步等待后仍能取回任务值，随后调用 startSpan('task-child') 会自动使用 Active Span 作为父级。

startSpan 和 startActiveSpan 的关键差别

API创建 Span自动成为当前 Span子 Span 自动继承
startSpan是否只有当前 Context 已含父 Span 时
startActiveSpan是是，仅 callback 生命周期是

无论哪种方式，都要显式调用 span.end()；激活和结束是两件事。

排错顺序

  1. 在异步操作前后打印 trace.getActiveSpan()?.spanContext()。
  2. 确认 SDK 注册了 Context Manager，且初始化早于业务模块。
  3. 确认 callback 真正在 context.with 或 startActiveSpan 内执行。
  4. 若只在跨服务后断链，检查 inject/extract 与 Header，不要先怀疑 ALS。
  5. 旧 callback API 丢 Context 时，用 AsyncResource 或显式绑定定位边界。

即时自测

为什么两个请求不能共享一个 currentTraceId？

因为等待 I/O 时另一个请求会覆盖它；事件循环恢复第一个请求时只能读到最后写入值。

Context 会自动跨 HTTP 或 RabbitMQ 吗？

不会。进程内由 Context Manager 维护；跨进程必须用 Propagator inject/extract Header。

为什么创建 Span 后仍可能没有 Active Span？

startSpan 只创建对象，不改变当前 Context；使用 startActiveSpan 或 context.with(trace.setSpan(...)) 才会激活。
